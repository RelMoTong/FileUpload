硬约束与执行纪律

不可变约束

  • 不使用任何数据库：生产代码、发布包和运行目录中不得包含 SQLite、数据库索引文件或数据库迁移逻辑。
  • 普通文件状态只允许使用有界、可校验、原子替换的 JSON/JSONL；它们是日志或恢复记录，不得演变为查询型数据库。
  • 保持现有 PySide6、Controller、Service、Worker、Protocol 的总体结构；不进行无关的大重写。
  • 一次只完成一个稳定编号任务；依赖未完成不得越级实施。
  • 不得用“代码已写完”代替完成：自动测试、故障注入、日志证据和回退点缺一不可。

范围保护

  • 每项修改开始前记录当前 git status，保护用户已有未提交变更。
  • 不顺手调整无关 UI、命名或格式；复用改造必须由具体风险或重复证据驱动。
  • 发现方案外高危问题时先登记，不直接扩大当前任务范围。
  • 出现数据丢失、误删、误报成功或恢复记录损坏时，立即停止后续任务并回退。

临时现场限制：改造完成前仅允许有人值守试运行；优先 SMB 单通道，开启备份，关闭去重与自动清理，源目录、目标目录、备份目录必须完全分离。

已确认问题与无数据库设计原则

风险域已确认现象目标不变量
FTP 结果连接对象并发变为 None 时仍可能返回成功；最终文件名可暴露半文件。没有远端确认就绝不成功；先临时名上传，验证后原子改名。
文件代际待归档记录只有路径，新文件覆盖同路径后可能被误移走。“上传完成”和“归档执行”必须绑定同一文件身份。
重试退避队列中的文件仍可被扫描，导致退避失效、重复上传。同一文件代际同一时刻只允许一个活动任务。
删除回收站不可用时人工清理可静默永久删除；手动与自动策略漂移。删除默认失败关闭；永久删除必须显式授权并产生审计证据。
恢复状态断点记录覆盖写入，进程中断后可变成空文件并遗留孤立分片。状态文件必须临时写、flush、fsync、replace，并保留可恢复备份。
路径检查只校验目录不相等，未阻止相互嵌套；UNC 检查在 UI 线程可能卡死。目录不得相同或互为祖先；远程探测有超时、可取消且不阻塞 UI。
数据库依赖清理与跨文件去重仍直接依赖两个 SQLite 仓储。发布代码零数据库；去重按运行期内存或目标文件即时校验，清理按流式扫描。
维护性网络暂停、清理、配置映射等逻辑多处重复，名称不同但职责相同。一项策略只有一个权威实现，其余调用者只传入参数和处理结果。

核心提交链：扫描并冻结文件身份 → 上传临时对象 → 校验远端 → 提交最终名 → 持久化精确代际归档记录 → 再校验身份 → 移动或安全删除源文件。

建议阅读路线

  1. src/main.py：确认组合根、依赖创建和发布探针。
  2. src/ui/main_window.py → Controller → Service：理解配置输入、校验和任务启动。
  3. src/workers/upload_worker.py：按“扫描、等待、网络、去重、上传、重试、归档”顺序阅读主流程。
  4. src/protocols/ftp.py 与 SMB 协议实现：核对成功定义、并发连接和最终提交语义。
  5. src/repositories/pending_archive_repository.py、src/resume_manager.py：核对跨进程状态和崩溃恢复。
  6. src/services/cleanup_service.py 与清理控制器：对比手动/自动删除路径和数据库耦合。
  7. src/config.py、模型设置对象、UI 保存/加载逻辑：定位重复配置源和无效字段。
  8. tests/、构建规格和依赖文件：最后确认行为契约是否覆盖真实发布包。
